Widget implementation options — what Portable SLM recommends

The chat surface today is a hand-authored custom element: customElements.define, attachShadow, template strings, ES modules. The only runtime dependencies in the package are @wllama/wllama and @wllama/wllama-compat. This page compares the alternatives a team will ask about, and states the recommendation. Switch the bar to compare.

The recommendation, in one rule

The widget stays framework-free; the host wraps it in its own idiom. A wrapper is ten lines and lives in the host's repository. A rewrite is a dependency every host inherits and a build step every host must reproduce — including the PHP page that has no bundler. Pick a framework for the host, never for the thing that has to mount inside all of them.

Adopt lit only if this component grows a real reactive graph — many interacting parts, template-heavy rendering, several contributors. It is the only option that keeps the public surface identical: same tag, same ::part(), same attributes, same CustomEvent. Everything else on this page changes who can load the widget.

The fact that decides most wrapper bugs: attributes vs properties

Attributes are strings in markup; properties are JS values on the element. Most frameworks' templates pass attributes. A function cannot cross an attribute, so onContext set in JSX or a Vue template silently does nothing — and a chat that never receives context answers from general knowledge, which looks like a model bug and is a wiring bug.

attribute (safe in any template)   model · system · tools · placeholder · allow-network · no-model-bar
                                   max-history · max-tokens · ctx        (read, not observed)
property  (needs a ref / el.api)   ai · onContext · onAnswer · approveTool · tools(array) · history
